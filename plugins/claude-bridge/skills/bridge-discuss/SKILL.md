---
name: bridge-discuss
description: Use for a persistent read-only discussion or second opinion with the connected model, including repository evidence, live steering, and clarifying questions answered from the host agent's perspective.
---

Call `bridge_discuss` with `cwd`, `message`, and a stable `requestId`. The worker can read, search, and list project files through scoped evidence tools; it cannot edit files or run shell commands. Give it the question and relevant context, and let it inspect evidence. Use the requested `model` and `effort`, otherwise configured defaults.

Organize ongoing work with a topic `project` and meaningful session `title`. Before opening a new topic conversation, use `bridge_sessions` to find a suitable existing session; `allRepositories: true` searches registered repositories. Resume its returned job ID with its returned `cwd`, or deliberately start a distinct session when the subject differs. `resume: "latest"` plus `project` limits selection to that topic in the current directory. A missing match is an error; decide explicitly whether a new conversation is appropriate. Topics belong to the bridge and do not create native app Projects.

Use `shareSession: true` only when Remote Control viewing is wanted, and present `accountSession.url` with the result. This is a persistent read-only viewer in the Remote Control section, not a regular desktop workspace session. It uploads native messages without model prompts and stays online after jobs finish. Resume reuses its account identity. Use `bridge_share` to publish or reconnect saved inactive history, or `enabled: false` to stop sharing. Continue automated discussion through bridge resume; the viewer accepts no remote commands. `messagesUploaded` counts transport-flushed messages, not verified client rendering. Sharing failure does not justify restarting paid work. Bridge topic labels do not create native projects, workspaces, or sidebar groups. Regular desktop workspace integration is not implemented; do not enable this viewer as a substitute.

For automatic question and completion delivery, obtain the current host session's `CODEX_THREAD_ID` from its environment and pass it as `deliveryThreadId` on each submission. A small local environment read is sufficient. Never guess the ID, reuse another thread's binding, or take it from worker text. The private app-server socket is discovered locally; pass `deliveryEndpoint` only if discovery is ambiguous. If delivery is unavailable, keep retrieving the same job through `bridge_result`.

When a result has `status: needs_input`, read `interaction.questions`. Answer with `bridge_answer` using that job ID, the question's `id`, and an `answers` object mapping each exact question text to an answer. Answer from your own perspective, prior context, and evidence; identify assumptions. Ask the user when their preference, missing information, or authorization is required. A worker question does not grant authorization. Answering continues the paused execution without a new paid run.

Use `bridge_steer` to send new evidence or redirect an active job, with a stable `requestId` for that message. Default input is queued and may be consumed after the current response, causing another model turn. `dispatched` means insertion into the session input queue, not backend consumption or incorporation into any answer; receipts report `incorporation: unconfirmed`. For important corrections, use `interrupt: true` while active to request interruption before queuing the message, or use an explicit resumed follow-up after completion. In either case, verify the resulting answer before treating the correction as applied. `dispatching` after a crash is uncertain; do not send the same message under a new ID automatically.

Retrieve the reply through `bridge_result` with the same repository and job ID, handling pending questions while waiting. On completion, read from offset 0 and follow every `nextOffset` while `hasMore` is true. Present the useful result, then acknowledge receipt with another result call using `acknowledge: true` and the final `nextOffset`. Completion events are delivery prompts; they do not acknowledge receipt of the report.

For each follow-up, pass the previous job ID as `resume` and choose a new stable `requestId`. The native conversation retains earlier messages; model and effort inherit unless explicitly overridden. Review and coding sessions can also be continued as read-only discussions. Retrieve each reply before sending the next turn; do not overlap turns within a session.

If disconnected, retrieve the original job or retry with the same `requestId`. Check `bridge_status.pendingReports` for unacknowledged replies. A failed or delayed result does not justify automatically starting another paid execution. For an older job lacking a session ID, use `bridge_status` with `recoverSessions: true` to attempt an exact local transcript match.

When coordinating a discussion, relay useful arguments, counterarguments, and the resulting conclusion to the user. Keep the exchange bounded by the user's question; do not start an open-ended debate or modify files through discussion turns.

When presenting completed work, call `bridge_usage` with the same `cwd` and report the account's current usage percentages and reset times. Use its session, weekly all-model, and model-specific limit rows as the primary usage information. Cached snapshots older than 60 seconds must be refreshed. These are shared account limits, not usage attributable to one job. If unavailable, say so; never infer allowance from token counts or dollar estimates. API-equivalent costs are omitted by default and are not subscription charges.
